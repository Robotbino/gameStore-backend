Backend Architecture Brief

Game Store API — Spring Boot · Spring Security · JPA

A stateless, JWT-secured REST API. Every request runs a filter gauntlet before it reaches a controller; controllers stay thin and delegate to services; services own the business rules and talk to MySQL through Spring Data repositories. This document walks the server top-to-bottom — the filter chain, the request lifecycle, the security model, the JWT, and the data model — with interactive layers, sequence diagrams, and traceable code paths.

Nothing reaches a controller until this layer says so. § 3 · Request Lifecycle

The filter gauntlet, in order

Order is everything in Spring Security — rules and filters are evaluated first-match-wins, top to bottom. This is the exact sequence every non-preflight request runs before your controller code executes.

Stage 1 · Framework CorsFilter Registered at HIGHEST_PRECEDENCE so preflight OPTIONS is answered before anything else. Only :5173 is allowed.
Stage 2 · Auth JWTAuthenticationFilter Skips /api/v2/auth/**. Otherwise reads the Bearer token, validates it, and puts an Authentication in the SecurityContext. Bad token → stays anonymous.
Stage 3 · Authorize authorizeHttpRequests Matches the path/method against the ordered rule list. No/anon auth on a protected route → 401; wrong role → 403.
Stage 4 · Dispatch DispatcherServlet Maps the URL to a handler method, deserializes the JSON body into a request object (Jackson), binds path variables.
Stage 5 · Handle @RestController Your code runs: delegate to a service, return a ResponseEntity. Jackson serializes the result back to JSON.
Why JWTAuthenticationFilter runs before UsernamePasswordAuthenticationFilter
addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class) slots the token filter ahead of the form-login filter. By the time authorization runs, the SecurityContext is already populated from the JWT — so there's no server-side session to look up. That's what makes the API stateless: the token is the entire proof of identity, re-presented on every request.
Why unauthenticated requests get 401, not the Spring default 403
exceptionHandling(...).authenticationEntryPoint(new HttpStatusEntryPoint(HttpStatus.UNAUTHORIZED)) overrides the default. A 401 tells the React app "your session is gone — redirect to login", which its axios interceptor keys on. /error is left permitAll so Boot's internal error forward isn't itself rewritten into a 401.

The rule checks for authority ROLE_ADMIN. That prefix isn't magic — it comes from the entity itself: getAuthorities() returns "ROLE_" + role.name(). hasRole("ADMIN") prepends ROLE_ for you, so the two meet in the middle.

§ 5 · Security Model

Who can call what

The whole access-control policy is one ordered list in SecurityConfiguration. Rules are evaluated top to bottom, and the first one that matches the request's method and path decides the outcome — so specific rules must come before general ones.

#MatcherRequirementRationale
1 /api/v2/auth/** permitAll You can't hold a token before you log in — auth endpoints must be open.
2 /error permitAll Boot forwards errors to /error; securing it would rewrite 403s into 401s.
3 GET /games/** permitAll Browsing the catalog is public; no login required to look.
4 /games/** POSTPUTDEL hasRole ADMIN Managing the catalog (add/update/delete) is admin-only.
5 /users/me authenticated Self-service: any logged-in user reads their own record. Must precede rule 6 — first match wins.
6 /users/** hasRole ADMIN All other user administration is admin-only.
7 anyRequest() authenticated The default-deny backstop: anything not listed still needs a valid token.
401 vs 403 — the difference that matters to the frontend
401 Unauthorized = "I don't know who you are" (no/invalid token) → the React axios interceptor wipes the token and redirects to /login. 403 Forbidden = "I know who you are, but you may not do this" (a USER hitting an ADMIN route) → the app shows a permission error without logging you out. Same status codes the frontend doc's failure catalog keys on.
Stateless by design — SessionCreationPolicy.STATELESS
Spring is told never to create or use an HttpSession. Every request must re-prove identity with its JWT. That means no server-side session store to scale or invalidate — but also that a token is valid until it expires (24h here), since there's nothing to revoke server-side.

§ 6 · JWT Anatomy

What's inside the token

A JWT is three Base64URL segments joined by dots: header.payload.signature. The first two are just encoded JSON — readable by anyone. The signature is what can't be forged. Hover any underlined part for detail.

The wire format (one string)

eyJhbGciOiJIUzI1NiJ9.eyJyb2xlIjoiQURNSU4iLCJzdWIi….4pcPyMD09olPSyXn…

Decoded payload (claims)

{
  "role": "ADMIN",
  "sub": "admin@gamestore.com",
  "iat": 1754000000,
  "exp": 1754086400
}

Signing JwtService.generateToken

Builds claims → sets subject/iat/exp → signWith(key, HS256) → compact(). The key is the Base64-decoded jwt.secret.

Verifying JwtService.isTokenValid

Subject must equal the loaded user's username and the token must not be expired. Parsing with the wrong key throws — caught by the filter.

Secret application.properties

jwt.secret is injected from an environment variable — it is not hard-coded in the repo. Rotating it invalidates every existing token at once.

How the password hash stays out of every response
Two independent guards. (1) On the entity, @JsonProperty(access = WRITE_ONLY) means Jackson accepts password on input but omits it on output. (2) The UserResponse record simply doesn't declare a password field — endpoints that map to the DTO can't leak it even by accident. Same reason the purchases collections are @JsonIgnored: it breaks the entity ↔ entity serialization cycle.

§ 8 · Exception → HTTP Mapping

One place turns exceptions into JSON

A @RestControllerAdvice catches exceptions thrown anywhere below the controllers and renders each as a consistent { "message": … } body with the right status — so services can just throw and stay ignorant of HTTP.

Thrown by the domainStatusResponse bodyWhen
ResourceNotFoundException 404 { message: "Game not found with id: 7" } getGameById / update / delete on a missing id.
BadCredentialsException
UsernameNotFoundException		 401 { message: "Invalid email or password" } Login with a wrong password or unknown email. Deliberately vague — doesn't reveal which.
MethodArgumentNotValidException 400 { message: "Validation failed", errors: { field: reason } } A @Valid request body fails a constraint. Keeps the message envelope, adds a per-field errors map.
DuplicateResourceException
EmailAlreadyExistsException		 400 { message: "Email already in use" } Duplicate email/username on register or user create. Kept at 400 (not 409) because the frontend keys on 400 for this case.
Exception (catch-all) 500 { message: "An unexpected error occurred" } The backstop for anything unmapped. Returns a generic message and logs the stack trace, so a server bug is never reported as the client's fault.
CONTRACT

Every error has the same shape

Always { "message": string }. The frontend's getApiErrorMessage() reads exactly this field, so backend and frontend agree on one envelope.

SECURITY

Login errors are intentionally vague

Bad password and unknown email both return the identical 401 message, so an attacker can't probe which emails are registered.
