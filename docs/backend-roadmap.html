Phase 0 · Unblock deployment

Six tasks between here and a link you can send someone

Every one of these is small. Together they are the difference between a project that exists on your laptop and one a reviewer can open. Do them in order — B1 gates B5, and B4 gates everything after it.

Gate

Nothing below Phase 0 is worth starting first. The briefs' own scorecard puts deployability at 2/10 and calls it "the load-bearing number" — it drags every other dimension down and is also the cheapest to fix.

Read the CORS origin from an env var

Blocker

The allowed origin is a hardcoded literal, so the API physically cannot accept a request from a deployed frontend. This is the single cheapest task on the board and it unblocks the most expensive one.

configuration/CorsConfig.java:21 — List.of("http://localhost:5173"). The placeholder CORS_ALLOWED_ORIGINS already sits commented-out at application-local.properties.example:22; nothing reads it yet.

Quick win

Create application-prod.properties: show-sql=false, logging at WARN, no security tracing. Today's noise is at application.properties:17,24-30.

Phase 1 · Data integrity

Stop letting Hibernate own the schema

B7 is the real gate here. A migration file already exists and reads as though Flyway is wired up — it is not. Every schema change after this point should arrive as a versioned migration, so this has to land before purchases or the catalog.

Actually wire Flyway up

Shipped ✓

Done (2026-08-08). flyway-core and flyway-mysql are now real dependencies; spring.flyway.baseline-on-migrate=true stamps existing databases at V1 without re-running the baseline, and spring.jpa.hibernate.ddl-auto is validate. Hibernate no longer touches the schema — drift fails startup.

Tests keep ddl-auto=create-drop against H2 with spring.flyway.enabled=false, because V1__baseline.sql is MySQL-flavoured (bit(1), ENGINE=InnoDB, hash-named FKs) and would fail — or worse, half-succeed — against H2. Unblocks B8; every schema change from here ships as a numbered migration.

Effort~30 min
ImpactHigh

Give games.price a real precision

Shipped ✓

Done (2026-08-08). V2__games_price_precision.sql narrows the column to decimal(10,2) via an in-place MODIFY, and Games.java gains @Column(nullable = false, precision = 10, scale = 2) so ddl-auto=validate stays happy.

$99,999,999.99 of headroom per row — absurdly generous for a store where real prices live at $0.99–$99.99, but tight enough to catch a stray decimal-shift bug at insert time instead of ten years from now. The migration is MySQL-only (MODIFY COLUMN); Flyway is off in tests, so H2 keeps building the schema from the entity mapping and sees the new precision that way. First real use of the V-numbered pipeline B7 built.

Effort~30 min
Depends onB7 ✓

Build the purchase & library endpoints

Shipped ✓

Done (2026-08-07). The entity and repository were already written and injected nowhere; now wired into POST /purchases and GET /purchases/me via a new PurchaseService and PurchaseController. The Library page was showing the whole catalogue and calling it "yours" — it now reads only what the user bought (pair P4 / F14, both shipped).

PurchaseRepository's findByUser / existsByUserAndGame are now consumed; findByUser gained an @EntityGraph fetch-join so the library response never serializes a lazy proxy. CheckoutResponse splits results into {purchased, alreadyOwned} so a repeat checkout is a safe no-op. Re-buy → 201/alreadyOwned, anonymous → 401, unknown id → 404 (curl-verified).

Effort~1 day
ImpactHigh
Pair withP4 · F14

Phase 2 · API quality & proof

Make the API shape defensible before features pile on top of it

Two inconsistencies are worth fixing before anything else consumes the API: service methods that no controller exposes, and /games returning raw entities while /users returns a DTO. Fix the shape once, not twice.

Expose server-side search, sort & pagination

Shipped ✓

Done (2026-08-08). One repository method backs three UX modes now: GamesRepository.search(q, genre, Pageable) — a JPQL query with optional filters, so ?q= alone, ?genre= alone, both together, or neither all use the same code path. Same treatment for UsersRepository.search(q, Pageable). The old dead methods (searchGames, getGamesByGenre, searchUsers) are gone; the unbounded findAllGames / findAllUsers are gone with them.

GET /games/all and GET /users/all now accept the standard Spring Data params (page, size, sort) plus q and genre. Default sort is id ASC so pagination is deterministic across pages. Max page size is capped at 100 in application.properties so a client can't ask for the whole table back and defeat the fix. Response envelope is a PagedResponse<T> record we own — Spring Boot 3.3 explicitly warns that PageImpl's JSON shape is not a stable contract. Pair-partner is F13: the frontend needs to stop consuming a raw array and start reading { content, page, size, totalElements, totalPages }.

Effort~half day
ImpactMedium
Pair withP5 · F13

Add a GameResponse DTO

Shipped ✓

Done (2026-08-08). Landed alongside B10 because shipping pagination first would have baked the raw Games entity into the paginated contract — exactly the asymmetry this card was created to fix. dto/GameResponse.java is a record mirroring UserResponse, with a static from(Games) factory; every /games/* route now returns GameResponse or PagedResponse<GameResponse>, never a raw entity.

The purchases back-reference is deliberately absent from the DTO — serialising it from a detached entity would throw LazyInitializationException. The DTO makes the omission a compile-time property instead of a runtime landmine.

Effort~2 hrs
ImpactConsistency
Pair withP5 · F13

No actuator dependency exists today. Expose health only; keep the rest closed.

Phase 3 · Headline features

The multi-day work, once the foundations hold

These are the items that make the project memorable rather than merely correct. They are last on purpose: each one is significantly more expensive if the schema, the API shape or the deploy story is still in flux underneath it.

RAWG catalog with a tiered read-through cache

Standout

The headline feature, and already designed down to TTLs: Caffeine (search 10 min · detail 24 h · genres 7 days) → MySQL shadow rows (UNIQUE(source, external_id), 14-day cached_at) → RAWG on a genuine miss, with 2s/4s timeouts and a 60-second circuit breaker.

Brief §11. Cache annotations belong on RawgCatalogProvider, not the controller — the brief argues this explicitly, and it is what protects the internal materialization path too.

Effortmulti-day
ImpactHigh · standout
Pair withP8 · F13/F15

Cart, checkout & order snapshots

Do it

The interesting part is the persistence distinction the brief already draws: a shadow row is a cache and may change; an order_item is history and may not. Price and title get snapshotted at purchase.

New orders / order_items tables — as V-numbered migrations, which is why B7 comes first. Guest carts migrate from localStorage on login.

Effortmulti-day
ImpactHigh

Rate-limit the auth endpoints

Later

/api/v2/auth/** is permitAll, skipped by the JWT filter, and completely unthrottled — an unlimited credential-stuffing surface. Low effort, but only matters once the app is publicly reachable.

bucket4j in the filter chain, or a Caddy-level rate limit on the auth path.

Effort~half day
Depends onB5

Refresh-token rotation

Later

The textbook-correct answer, and genuinely optional here — the brief's position is that a 24-hour token with no revocation is a defensible portfolio trade-off. Do it to show you know the pattern, not because the current design is broken.

Short-lived access token + httpOnly refresh cookie on a scoped path. Meaningless without the matching client-side silent renew.

Effort~1 day
ImpactLow–Medium
Pair withP9 · FE renew

Cross-stack · Recommended Pairings

Nine places where doing one side alone is wasted work

The backend and frontend live in separate repos, which makes it easy to finish a task that cannot be verified — or worse, ship an API shape the client then has to absorb twice. These pairs should be tackled in the same sitting. This section is duplicated verbatim in the frontend roadmap.

P1
BackendB1 · CORS origin from envCorsConfig.java:21
FrontendF1 · single API base-URL constantservices/api.ts:5 · DemoPage.tsx:9

Why together: neither is testable on its own. The backend change has no observable effect until a non-localhost origin calls it, and the frontend change has nowhere to point until the backend accepts one. Combined, they are about an hour and they are the deploy unblocker.

P2
BackendB4 + B5 · Docker & Oracle VMcompose · Caddy · TLS
FrontendF2 · Cloudflare Pages deployVITE_API_URL at build time

Why together: the dependency is circular. The SPA bundle needs the API's public origin baked in at build time, and the API's CORS_ALLOWED_ORIGINS needs the Pages domain. Sequence it in one session: bring the API up first, build the SPA against its URL, then set the CORS value to the Pages host and redeploy the API.

P3
BackendB6 · backend briefs → Pagesarchitecture · learning guide · roadmap
FrontendF3 · frontend briefs → Pagesarchitecture · catalog pivot · roadmap

Why together: six documents across two repos, but one story. The existing cross-doc switcher already links between repos using relative filesystem paths — those break the moment the docs are served from two different Pages sites, so the URLs have to be fixed on both sides at once or half the doc set becomes orphaned.

P4
BackendB9 · purchase & library endpointsPurchaseRepository, currently unused
FrontendF14 · real LibraryPageLibraryPage.tsx:15

Why together: the Library page currently calls getAll() and shows every game in the store as though the user owned it. The page is actively misleading, and neither half fixes that alone — endpoints with no consumer prove nothing, and the page cannot be corrected without them.

P5
BackendB10 + B11 · Page<GameResponse>GamesService.searchGames():32
FrontendF13 · consume Page, drop client filtergameService.search → getAll()

Why together: shipping pagination before the DTO forces the frontend through two breaking rewrites — once for the envelope, once when the entity becomes a DTO. Land the final shape and its only consumer in one go.

P6
Backendduplicate-email 400 → 409GlobalExceptionHandler
FrontendF11 · error handling reworkutils/apiError.ts

Why together — and never apart: the brief documents 400 as a deliberate choice "because the frontend keys on 400 for this case", and it does. Changing the status server-side in isolation silently breaks the registration error message with no test failure to catch it. This is the clearest example on the board of a change that is only safe as a pair.

P7
BackendB13 · mvnw verify jobSurefire + Failsafe, H2
Frontendlint + tsc -b + build jobno CI exists in either repo

Why together: a badge that only covers one repo is worse than none — it implies coverage it does not have. Two jobs, authored together, so "green" means the whole stack builds on a clean machine.

P8
BackendB16 · RAWG + tiered cacheCaffeine → shadow rows → RAWG
FrontendF13 / F15 · query layer + degraded banner?search= & page= in the URL

Why together: the design's best detail is the degraded response flag for when RAWG is down and the cache is serving stale rows — and a flag nobody renders is just a field. The pairing also retires the 501 stub button on the admin dashboard, which is currently the most visible unfinished thing in the UI.

P9
BackendB19 · refresh-token rotationhttpOnly cookie + short access token
Frontendsilent renew in the interceptorservices/api.ts:22-34

Why together: today a token that dies mid-session is discovered only when the server rejects a request, and the client responds with a hard page reload. Issuing refresh tokens the client never exchanges changes nothing a user would notice.

Discarded · Quick wins that aren't

Six shortcuts that look cheap and cost more later

Each of these is genuinely fast to do and would each create work to undo. They are listed so the decision is on the record rather than rediscovered.

Flip ddl-auto to validate now

Skip

Looks like a one-word hardening win. Without Flyway actually wired up (B7) there is no migration runner to create the schema, so the app simply refuses to start.

Put @Cacheable on the controllers

Skip

Fast to add, and would be deleted during B16. The brief argues the cache belongs on the provider precisely so the internal materialization path is protected too — controller-level caching misses that and has to be unwound.

Implement the RAWG sync ad hoc

Skip

Filling in the 501 stub with a quick fetch-and-save discards a design that already exists: dto/GameRequest.java:16-18 documents a future RawgImportService mapping RAWG JSON onto that record, so import reuses the same validation as the API. A shortcut here throws that reuse away.

Expose /games/search returning a plain List

Skip

Half an hour, and it guarantees a second breaking change the moment pagination lands — plus a second frontend rewrite. If the method is worth exposing, expose it with the final envelope.

Change users.id from Integer to Long

Skip

The inconsistency with games.id is real and slightly ugly. V1__baseline.sql already calls it accepted debt: changing a primary-key type that other tables reference is genuine risk for a cosmetic payoff.

Move duplicate-email from 400 to 409 on its own

Skip

Correct in isolation, breaking in practice — the frontend keys on 400. Valid only as pairing P6, never as a standalone tidy-up.

Also deliberately out of scope, per the architecture briefs: Kubernetes · Redis · microservices · Kafka / event sourcing / CQRS · GraphQL · Terraform. One bounded context does not need any of them, and reaching for them reads as résumé-driven complexity.
