§ 1 · Orientation

How to read this codebase

Four layers, top to bottom. A request enters through security, gets routed to a controller, the controller delegates to a service, the service talks to a repository, the repository talks to the database. Nothing skips a layer.

First reading exercise: follow one request all the way down

Open five files in this exact order and read only the part each one contributes to a single GET /users/me call:

  1. JWTAuthenticationFilter — reads the token and puts the user in the SecurityContext.
  2. SecurityConfiguration — matches /users/me and decides "authenticated? yes → proceed".
  3. UsersController.getMe — receives the principal Spring injected for it.
  4. UserResponse.from — maps the entity onto the response record.
  5. GlobalExceptionHandler — where a thrown exception would have gone if anything failed.

If you can narrate those five files back to yourself as one story, you understand this app. Everything else is variations on that theme.

§ 2 · Design patterns

The patterns in this code, with the problem each one solves

A pattern isn't a decoration — it's a solution to a specific problem. If you can name the pattern and the pain it removes, you understand the choice. Every row below is a pattern that's really in this codebase, with the file where you can see it working.

PatternWhere it livesThe problem it solves
Dependency Injection GoF-adjacent @RequiredArgsConstructor + final fields — every service and controller Classes ask for their collaborators instead of creating them. Testable, and no new UserRepository() buried in a service constructor.
Layered architecture controllers → services → repositories HTTP concerns stop at the controller edge; business rules stop at the service edge; SQL stops at the repository edge. Each layer changes for one reason.
DTO (Data Transfer Object) dto/UserResponse · dto/GameRequest · dto/Create/UpdateUserRequest The API contract is decoupled from the database schema. A password column on the entity can't leak into a JSON response because the DTO doesn't declare one.
Static Factory Method UserResponse.from(users) Names the mapping direction at the call site. Effective Java, Item 1: prefer static factories to constructors when the name adds information.
Builder GoF Users.builder() · Games.builder() (via Lombok @Builder) Readable construction of objects with many optional fields. Effective Java, Item 2: builder over telescoping constructors.
Repository UserRepository · GamesRepository · PurchaseRepository An interface abstracts data access. Method names like findByTitleContainingIgnoreCase become SQL at runtime — no hand-written JDBC.
Proxy GoF Spring Data repository impls · @Transactional wrappers Behaviour (SQL execution, transaction begin/commit, security checks) is added around a class without touching your source. The object you inject is a subclass Spring made at runtime.
Chain of Responsibility GoF The servlet filter chain Each filter does one job (CORS, JWT decoding, authorization) and calls filterChain.doFilter(...). New concerns are added by inserting another link, not by editing existing filters.
Template Method GoF extends OncePerRequestFilter → override doFilterInternal The framework owns the algorithm; you fill one hook. That's why you never write "make sure this only runs once per request" — Spring's parent class already does it.
Strategy GoF PasswordEncoder ← BCryptPasswordEncoder (in ApplicationConfig) Callers depend on the interface, not the algorithm. Swapping bcrypt for Argon2 is one line in one file, and no calling code changes.
Adapter GoF Users implements UserDetails A JPA entity is adapted to satisfy the shape Spring Security expects. Authentication can load a "security principal" straight from the users table with no extra type in the middle.
Front Controller DispatcherServlet (Spring MVC, wired by Boot) One entry point routes every incoming request to the right handler. You never write a URL-to-method table by hand — you write annotations on methods and the front controller does the dispatch.
Singleton (default bean scope) Every @Service, @Component, @RestController One instance per app. Cheap and fast — and the reason mutable fields on a bean are dangerous: every request sees the same object. Beans should be stateless.

§ 3 · Real fixes from this repo

Beginner mistake vs. best practice

Every card below is a change this codebase really made. The "mistake" panel is code that was once here (or almost was); the "clean code" panel is what replaced it, and the note explains why the fix matters in practice.

1. Field injection → constructor injection on a final field

DISpring
BEGINNER · @Autowired on a field
@RestController
public class GamesControllers {
    @Autowired
    private GamesService gamesService;  // mutable, not final
}
CLEAN · constructor injection via Lombok
@RestController
@RequiredArgsConstructor
public class GamesControllers {
    private final GamesService gamesService;
}

Why this bites you: field injection hides the dependency (no constructor to look at), can't be final, and can't be exercised in a plain unit test without reflection. Constructor injection makes the dependency required and makes the class trivially testable — you just call new with mocks.

2. Returning the JPA entity → returning a UserResponse DTO

SecurityDTO
BEGINNER · entity out the door
@GetMapping("/all")
public ResponseEntity<List<Users>> getAllUsers() {
    return ResponseEntity.ok(service.findAllUsers());
    // Response includes password hash unless a Jackson
    // annotation happens to be in place.
}
CLEAN · map to a record with no password field
@GetMapping("/all")
public ResponseEntity<List<UserResponse>> getAllUsers() {
    List<UserResponse> users = service.findAllUsers().stream()
            .map(UserResponse::from)
            .toList();
    return ResponseEntity.ok(users);
}

Why this bites you: the "safety" of hiding the password with a @JsonIgnore is incidental — one removed annotation and the hash is public. The DTO makes safety structural: the record doesn't declare a password field, so no code path can serialise one, even by accident.

3. getUsername() vs getUserName() — today's real bug

JavaSpring Security
BEGINNER · call the UserDetails override by accident
public static UserResponse from(Users user) {
    return new UserResponse(
        user.getId(),
        user.getUsername(),  // ← UserDetails override → returns EMAIL
        user.getEmail(),
        user.getRole().name(),
        user.getPoints());
}
CLEAN · use the entity field getter
public static UserResponse from(Users user) {
    return new UserResponse(
        user.getId(),
        user.getUserName(), // ← real Lombok getter for the field
        user.getEmail(),
        user.getRole().name(),
        user.getPoints());
}

Why this bites you: the interface method getUsername() (from UserDetails) is overridden here to return the email — that's how Spring Security looks users up. Lombok's generated getUserName() returns the real username field. Compiler can't tell you apart. The regression test in UsersEndpointsIT now asserts both fields are what a human would expect.

4. RuntimeException → 400 catch-all → specific mappings + Exception → 500

@RestControllerAdvice
BEGINNER · blame the client for every bug
@ExceptionHandler(RuntimeException.class)
public ResponseEntity<?> handleRuntime(RuntimeException e) {
    return new ResponseEntity<>(
        Map.of("message", e.getMessage()),
        HttpStatus.BAD_REQUEST);
    // A NullPointerException from a server bug
    // just became "400 Bad Request".
}
CLEAN · specific handlers + honest 500 backstop
@ExceptionHandler({DuplicateResourceException.class,
                    EmailAlreadyExistsException.class})
public ResponseEntity<?> handleDuplicate(RuntimeException e) {
    return status(BAD_REQUEST).body(msg(e.getMessage()));
}

@ExceptionHandler(Exception.class)
public ResponseEntity<?> handleUnexpected(Exception e) {
    log.error("Unhandled exception", e);
    return status(INTERNAL_SERVER_ERROR)
        .body(msg("An unexpected error occurred"));
}

Why this bites you: 4xx says "the client made a mistake"; 5xx says "the server did". Mapping every RuntimeException to 400 lies to callers and hides your stack traces. The clean version logs the trace and returns a generic 500 message — the client sees "something went wrong", you see the cause in the logs.

5. throw new RuntimeException(...) → a named domain exception

Java
BEGINNER · reach for the base type
if (userRepository.existsByEmail(user.getEmail())) {
    throw new RuntimeException("Email already in use");
}
CLEAN · a type the handler can catch specifically
if (userRepository.existsByEmail(user.getEmail())) {
    throw new DuplicateResourceException("Email already in use");
}

Why this bites you: a bare RuntimeException can't be routed anywhere without also catching every other unchecked exception in the app. A named class lets the @ExceptionHandler target this specific error — and lets tests assert on the type, not on a fragile message string.

6. @RequestBody Users → @Valid @RequestBody CreateUserRequest

Security · mass assignmentDTO
BEGINNER · bind the entity directly
@PostMapping("/add")
public ResponseEntity<Users> addUser(@RequestBody Users user) {
    return ResponseEntity.status(CREATED).body(service.addUser(user));
    // Client controls EVERY field — role, points, id.
    // POST { "role": "ADMIN" } → self-promotion.
}
CLEAN · validated DTO, controller maps to entity
@PostMapping("/add")
public ResponseEntity<UserResponse> addUser(
        @Valid @RequestBody CreateUserRequest request) {
    Users toCreate = Users.builder()
            .userName(request.userName())
            .email(request.email())
            .password(request.password())
            .role(request.role() != null ? request.role() : Role.USER)
            .build();
    Users created = service.addUser(toCreate);
    return ResponseEntity.status(CREATED).body(UserResponse.from(created));
}

Why this bites you: binding the entity is a mass-assignment vulnerability. The DTO gives you a whitelist of accepted fields, and @Valid enforces every constraint annotation on it (@Email, @Size(min=8), @NotBlank) before your handler runs.

7. Route order — first match wins

Security
BEGINNER · general rule first
.requestMatchers("/users/**").hasRole("ADMIN")
.requestMatchers("/users/me").authenticated()
// /users/me matches /users/** FIRST and gets ADMIN-gated,
// so no ordinary user can ever read their own record.
CLEAN · specific rule first
.requestMatchers("/users/me").authenticated()
.requestMatchers("/users/**").hasRole("ADMIN")

Why this bites you: Spring Security evaluates matchers top to bottom and stops at the first one that matches. The rule you meant to be the exception has to appear before the rule it's an exception to. Same principle applies to if / else if ladders in your own code.

8. JpaRepository<Users, Long> with an Integer id

Java generics
BEGINNER · guessed the id type
public interface UserRepository
    extends JpaRepository<Users, Long> { }

// Compiles, then at runtime:
// "provided id of the wrong type for class ...Users.
//  Expected: Integer, got Long"
CLEAN · match the entity's id type
public interface UserRepository
    extends JpaRepository<Users, Integer> { }

Why this bites you: generics get erased at runtime — so the compiler happily accepts a repository whose id-type disagrees with the entity's @Id field, and Hibernate only notices on the first query. Read the entity's id declaration before writing the repository.

9. double price → BigDecimal price

OCA · numeric types
BEGINNER · use a primitive for money
@Column(nullable = false)
private double price;
// double a = 0.1, b = 0.2;
// a + b == 0.3   →   false  (it's 0.30000000000000004)
CLEAN · exact decimal for currency
@Column(nullable = false)
private BigDecimal price;
// Exact base-10 arithmetic; no accumulated rounding.

Why this bites you: double and float are base-2 floating point and can't represent most decimal fractions exactly. A cent lost per transaction across a million transactions is a real bug. BigDecimal (immutable, exact) is the right type for money. This exact question appears on 1Z0-808 exam papers.

10. @OneToMany without mappedBy → phantom join table

JPA
BEGINNER · both sides declare ownership
// In Users:
@OneToMany private List<Purchases> purchases;

// Hibernate assumes it owns BOTH sides and generates
// a users_purchases join table you never asked for.
CLEAN · one owner (the FK holder) + mappedBy
// In Users:
@OneToMany(mappedBy = "user",
           cascade  = CascadeType.ALL,
           orphanRemoval = true)
private List<Purchases> purchases;

// mappedBy = "user" says: "Purchases owns the FK column,
// I just navigate to it." No junk table.

Why this bites you: in a bidirectional JPA relationship exactly one side is the owner — the one whose table holds the foreign key. The other side declares mappedBy = "<field name on the owner>". Skip it and Hibernate makes up its own join table, mysteriously duplicating rows.

11. Role taken from the request body → derived server-side from admin.email

Security · authorization
BEGINNER · trust the client
public AuthenticationResponse register(RegisterRequest req) {
    Users u = Users.builder()
        .email(req.getEmail())
        .role(req.getRole()) // ← client sets their own role
        .build();
    ...
}
// POST /register { "email": "...", "role": "ADMIN" }
// You are now the admin.
CLEAN · derived from configured admin email
@Value("${admin.email}")
private String adminEmail;

Role role = request.getEmail().equalsIgnoreCase(adminEmail)
        ? Role.ADMIN
        : Role.USER;

Why this bites you: any input the client controls is untrusted. Authorization decisions must come from data you own (a configured value, a database record, a signed token) — never from a field the caller can rename in Postman.

12. Committed jwt.secret → ${JWT_SECRET} from the environment

Security · secrets
BEGINNER · commit the secret
# application.properties (checked into git)
jwt.secret=hR8fA...actualBase64Key...=
CLEAN · resolve from the environment
# application.properties
jwt.secret=${JWT_SECRET}
# The value lives outside git — env var, .env not committed,
# secrets manager, etc.

Why this bites you: anything you push to a public repo is compromised the moment it lands — assume scrapers are watching. Rotating a leaked JWT key invalidates every token in the wild, but the alternative is worse. Move all secrets to environment variables or a secrets manager from day one.

§ 4 · Spring, in depth

Annotations — what they do, and what they secretly do

A Spring annotation is a request to the framework: "please generate the plumbing I would otherwise write by hand." Every card below expands to the mechanism behind the annotation, not just its name.

@RestController — @Controller + @ResponseBody

@RestController is @Controller + @ResponseBody on every method. That means method returns are handed to Jackson (or whichever HttpMessageConverter matches Accept) and serialized to JSON, instead of being treated as view names for a template engine.

Under plain @Controller, returning List<Users> would ask Spring to render a view called "[Users{id=1,...}]" — and you'd get a 500. This is quiz Q1.

@Service, @Repository, @Component — same mechanism, different vocabulary

All three tell Spring "instantiate this class as a bean". They're semantically distinct so a reader can tell what role a class plays: @Service = business logic, @Repository = data access (and gets JPA exception translation), @Component = the generic fallback for infrastructure classes like filters.

Pick the most specific one that fits. It costs nothing at runtime and it documents intent.

@Configuration + @Bean — factory methods for beans

@Configuration marks a class as a source of bean definitions. Every method annotated @Bean becomes a factory Spring calls once (per scope; default is singleton) and registers the result.

Look at ApplicationConfig — passwordEncoder(), authenticationProvider(), userDetailsService() are all beans wired together by return type and by parameters. That's why the classes never say new BCryptPasswordEncoder(): they ask for a PasswordEncoder and Spring supplies whichever bean is currently registered under that type.

@Autowired — and why you don't see it here

On a constructor, @Autowired is redundant since Spring 4.3 when the class has exactly one constructor. Lombok's @RequiredArgsConstructor generates that single constructor from final fields, so injection happens without @Autowired appearing anywhere. Result: dependencies are visible in the constructor signature; the code stays annotation-light.

You'll still see @Autowired on field injection — that's the antipattern this repo removed.

@Transactional — the proxy trap that catches everyone once

@Transactional works via a proxy: Spring subclasses your service and wraps the annotated method in a begin/commit/rollback. So calls made through the proxy get the transaction. Calls made within the same class (this.someMethod()) bypass the proxy and lose the transaction — this is the "self-invocation trap".

By default, rollback fires on unchecked exceptions only. If you want checked exceptions to trigger rollback: @Transactional(rollbackFor = SomeChecked.class).

@Valid and @RequestBody

@RequestBody asks Jackson to deserialize the incoming JSON into the parameter type. @Valid then runs every Bean Validation constraint on that object (@NotBlank, @Email, @Size, @Positive, etc.). If validation fails, Spring throws a MethodArgumentNotValidException before your handler runs — GlobalExceptionHandler turns it into a 400 with a per-field errors map.

@RestControllerAdvice + @ExceptionHandler — one place, all errors

@RestControllerAdvice is @ControllerAdvice + @ResponseBody. Any @ExceptionHandler method inside it applies to exceptions thrown by any controller in the application — so services just throw and stay ignorant of HTTP. Everything error-shaped funnels into GlobalExceptionHandler in this repo.

@Entity, @Table, @Column — mapping objects to rows

@Entity tells JPA "this class is a persistent type". @Table overrides the generated table name; @Column overrides the column name or adds constraints (nullable = false, unique = true, columnDefinition = "TEXT"). Hibernate builds a metamodel from these at boot and generates SQL on demand.

spring.jpa.hibernate.ddl-auto=update lets Hibernate evolve the schema to match the entities on startup — a lovely convenience in dev and an operational hazard in prod.

@OneToMany / @ManyToOne and FetchType.LAZY

Bidirectional relationship rule: one side owns the foreign key. The other side declares mappedBy = "<field name on the owning side>". This is Mistake #10 above.

FetchType.LAZY defers loading until you actually navigate the association — needed for @ManyToOne or you'll pull the whole graph on every query. Beware LazyInitializationException: if you try to load a lazy field outside a transaction (e.g. from a detached entity like the JWT principal), it throws.

@Enumerated(EnumType.STRING) — and why not ORDINAL

EnumType.STRING stores the enum's name ("USER", "ADMIN"). EnumType.ORDINAL stores its position (0, 1). Reorder the enum's constants once and every ordinal in the database refers to the wrong value with no compiler warning. Use STRING.

@JsonIgnore / @JsonProperty(access = WRITE_ONLY)

@JsonIgnore tells Jackson to omit this field in both directions. @JsonProperty(access = WRITE_ONLY) accepts the field on input but omits it on output — the pattern for passwords on entities. Both are incidental safety though; the structural fix is a DTO that never declares the field in the first place (see Mistake #2).

@AuthenticationPrincipal — inject "the current user"

@AuthenticationPrincipal is a parameter-level annotation that pulls SecurityContextHolder.getContext().getAuthentication().getPrincipal() and casts it to the parameter type. In this app the principal is a Users (because userDetailsService() returns the entity), so @AuthenticationPrincipal Users user is the clean way to get the current user with no boilerplate.

@Value("${...}") — pull config into a bean

@Value injects a resolved property (from application.properties, an env var, or a yaml file) into a field. ${JWT_SECRET} resolves in this order: the environment, then system properties, then application.properties. That's the mechanism behind Mistake #12.

§ 5 · Java fundamentals, exam-badged

What this codebase teaches you about the language

Every concept below carries a badge. The OCA 1Z0-808 exam covers Java SE 8, but this codebase is Java 17 — so some of the most idiomatic code here (records, var, Stream.toList()) is explicitly outside the exam. Read the badges before assuming.

On 1Z0-808Autoboxing

Integer vs int — the NPE that motivated today's null-guard

In UsersService.updateUser, if a client sends an update with no points field, Jackson leaves the DTO's Integer points as null. Autoboxing a null Integer into an int throws NullPointerException. That's why the fix reads:

if (updatedUser.getPoints() != null) {
    existing.setPoints(updatedUser.getPoints());
}

OCA trap: the boxing/unboxing question shows up on 1Z0-808 as a "why does this line NPE?" puzzle. Answer: assignment to an int triggers .intValue() on null.

On 1Z0-808enum

enum Role { USER, ADMIN }

An enum is a class that's declared with a fixed set of instances. You can add fields, constructors, and methods to it. Role.ADMIN.name() returns "ADMIN" — that's what gets stored in the DB (via @Enumerated(EnumType.STRING)) and what gets set as a claim in the JWT.

OCA trap: know the difference between name() (final, returns the constant name) and toString() (overrideable).

On 1Z0-808Interfaces

Interfaces with default methods — UserDetails has them

Since Java 8, an interface can carry method implementations via default. That's how UserDetails can grow methods without breaking existing implementers. When you write Users implements UserDetails you can leave the defaults alone (they return true for the "non-locked", "non-expired" methods here) and only override the ones you care about.

On 1Z0-808Multi-catch

Multi-catch: catch (JwtException | UsernameNotFoundException e)

From JWTAuthenticationFilter. One catch block handles multiple exception types joined with |. The parameter is effectively final.

OCA trap: the types in a multi-catch must not be in an inheritance chain with each other — you can't write catch (RuntimeException | IllegalStateException e).

On 1Z0-808Lambdas

Lambda implementing a functional interface

From ApplicationConfig.userDetailsService():

return username -> repository.findByEmail(username)
        .orElseThrow(() -> new UsernameNotFoundException("User not found"));

UserDetailsService is a functional interface (one abstract method, loadUserByUsername). The lambda is the implementation. This is textbook 1Z0-808 material.

On 1Z0-808Optional

Optional.orElseThrow

return userRepository.findById(id)
    .orElseThrow(() -> new ResourceNotFoundException("User not found with id: " + id));

Optional was added in Java 8. orElseThrow(Supplier) pulls the value or throws what the supplier returns. Use it instead of .get() — .get() throws NoSuchElementException with no diagnostic.

On 1Z0-808String

String immutability and equalsIgnoreCase

request.getEmail().equalsIgnoreCase(adminEmail) — case-insensitive comparison without allocating lowered copies. Strings are immutable, so pooling / literal caching makes == sometimes look like it works. It doesn't (reliably) — always compare with .equals() or .equalsIgnoreCase(). Big 1Z0-808 topic.

Java 14+ · not on 1Z0-808

record — used everywhere in dto/

public record UserResponse(
        Integer id, String userName, String email,
        String role, Integer points) { ... }

A record gives you: private final fields, a canonical constructor, accessors, and equals/hashCode/toString for free. Immutable by construction. Not on 1Z0-808 — if you're prepping for that exam and you see the plain-class equivalent, that's what you'll be tested on.

Java 9+ · not on 1Z0-808

List.of(...) — immutable collection factory

From Users.getAuthorities():

return List.of(new SimpleGrantedAuthority("ROLE_" + role.name()));

Returns an unmodifiable list. Cheaper and clearer than Collections.unmodifiableList(Arrays.asList(...)). Not on 1Z0-808; on the exam you'd use Arrays.asList or a mutable list.

Java 16+ · not on 1Z0-808

Stream.toList()

List<UserResponse> users = service.findAllUsers().stream()
        .map(UserResponse::from)
        .toList();

Shorter than .collect(Collectors.toList()) and returns an unmodifiable list. 1Z0-808 equivalent: .collect(Collectors.toList()) — and Streams beyond the basics live in the OCP exam, not the OCA.

Java 10+ · not on 1Z0-808

var — local variable type inference

Used in AuthenticationService: var newUser = Users.builder().... The compiler infers the type from the initializer. Only works for local variables — not fields, method params, or return types. Not on 1Z0-808.

OCP (1Z0-809)Streams

Method references: UserResponse::from

ClassName::method is a shorthand for a lambda that just calls that method. Equivalent to user -> UserResponse.from(user). Passed as a Function to Stream.map. Streams and method references are covered on the OCP exam, not on 1Z0-808.

On 1Z0-808Exceptions

Checked vs unchecked exceptions

Every custom exception in this repo (ResourceNotFoundException, DuplicateResourceException, EmailAlreadyExistsException) extends RuntimeException. That's unchecked — no throws clause required, no boilerplate for callers, and Spring's @Transactional default rollback applies. Checked exceptions (things that extend Exception directly) force every caller to handle or declare them. Prefer unchecked for programming errors; use checked for genuinely recoverable conditions. 1Z0-808 examinable.

On 1Z0-808equals / hashCode

Why every entity here has custom equals and hashCode

JPA entities have a mutable id (null before the first save, populated after). If equals compares all fields, two instances of "the same" user look unequal until they're both saved. The entities in this repo compare by id only, and hashCode returns getClass().hashCode() so the value is stable across the entity's lifecycle. Classic JPA hazard — and equals/hashCode contracts are 1Z0-808 territory.

On 1Z0-808Modifiers

final on fields — what it actually guarantees

final on a field means: assigned exactly once, either at declaration or in the constructor. It does not mean the referenced object is immutable — you can still mutate the object the field points at. In this codebase final on injected fields is a contract: "this dependency is set at construction and never replaced".

On 1Z0-808Access

Access modifiers — public, protected, package-private, private

The DTOs are public records because the API surface reads them. Fields on entities are private and accessed via Lombok's generated getters. Package-private (the default — no modifier) is genuinely useful for helpers; it's not "just public that forgot the word".

§ 7 · Assessment prep

What rigorous technical assessments actually probe

This section is calibrated to the kind of thing graduate programmes and hiring assessments (BBD-style, for example) really test — not fact recall, but the ability to justify a design choice. Honest caveat: this is general preparation for that class of assessment, not modelled on any specific company's paper.

The four things they're testing under the code question

  1. Can you explain why? "Why is this a service, not a helper class in the controller?" — the answer is layering, testability, and the transaction boundary.
  2. Do you know when to reach for a pattern? Not "list five design patterns", but "you have three payment providers with different APIs — how do you structure that?" (Strategy, and here's why.)
  3. Can you spot a security issue in code you didn't write? Mass assignment, IDOR, secrets in git, weak password hashing, missing role check — all covered in §3 above.
  4. Can you talk about trade-offs? "Why 400 for duplicate email and not 409?" — the answer is a real trade-off between HTTP correctness and frontend contract stability, not a right/wrong.

SOLID walkthrough on this codebase

  • S — Single Responsibility. Controllers do HTTP, services do business rules, repositories do persistence. The exception handler is a single class because "turn thrown exceptions into JSON" is one responsibility.
  • O — Open/Closed. The filter chain is open for extension (add a link) and closed for modification (existing filters stay put).
  • L — Liskov substitution. Users implements UserDetails — anywhere Spring Security expects a UserDetails, a Users works, without surprising the caller.
  • I — Interface segregation. UserDetailsService is one method. Callers don't depend on stuff they don't use.
  • D — Dependency Inversion. UsersService depends on PasswordEncoder (interface), not BCryptPasswordEncoder (concrete). Swapping the algorithm is one line in ApplicationConfig.

Things you should be able to draw on a whiteboard

  • The filter chain, in order, with what each filter does.
  • The four layers of the app, and one file name per layer.
  • The register flow: what happens between the POST arriving and the token going out.
  • The rule table from SecurityConfiguration, in order, with an explanation of why "first match wins" matters.
  • The exception → HTTP status mapping (200/201/204 successes and 400/401/403/404/500 errors).
