From doubt to confidence — how to navigate this codebase

This document is a companion to architecture.html. That document explains what the backend does. This one explains why. It is for a developer who can already read the code but does not yet trust their own judgement about it. It compares real "beginner mistake" and "best practice" examples from the history of this repository. It also gives a detailed section on Spring, an OCA-badged tour of the Java features that the code uses, and click-to-reveal quizzes.

How to read this document. Read the section list quickly, then go to the section that you need. Some code snippets name the class that they come from, and every quiz cites a source file. Open the file to see the pattern in context. Every Java concept has a badge: On 1Z0-808, Java 9+ · NOT on 1Z0-808 or OCP (1Z0-809). Thus, if you study for an exam, you always know whether the topic that you read is on the exam.

§ 1 · Orientation

How to read this codebase

The app has four layers, from top to bottom. A request enters through security, and then DispatcherServlet sends it to a controller. The controller delegates to a service. The service talks to a repository, and the repository talks to the database. No request skips a layer.

First exercise: follow one request through all the layers

Open these five files in this exact order. In each file, read only the part that it contributes to a single GET /users/me call:

  1. JWTAuthenticationFilter — reads the token and puts the user in the SecurityContext.
  2. SecurityConfiguration — matches /users/me and decides "authenticated? yes → proceed".
  3. UsersController.getMe — receives the principal that Spring injected for it.
  4. UserResponse.from — maps the entity onto the response record.
  5. GlobalExceptionHandler — where a thrown exception goes if something fails.
flowchart TB
  Req["GET /users/me<br/>Authorization: Bearer …"]
  Req --> Filter["1 · JWTAuthenticationFilter<br/>reads token → SecurityContext"]
  Filter --> Sec{"2 · SecurityConfiguration<br/>authenticated?"}
  Sec -->|"no / bad token"| E401["401 Unauthorized<br/>never reaches your code"]
  Sec -->|"yes"| Ctrl["3 · UsersController.getMe<br/>receives the principal Spring injected"]
  Ctrl --> Map["4 · UserResponse.from<br/>entity → response record"]
  Map --> Resp["200 OK<br/>id · email · role"]
  Ctrl -.->|"5 · anything throws"| GEH["GlobalExceptionHandler<br/>exception → JSON + status"]

This diagram shows the same five files as one flow, with numbers that match the list above. Hover over a line in that list to highlight its box here, or click a box to go back to the line. Everything green is the happy path, in which each layer makes exactly one call to the next. The amber pair is the security gate that a request passes before any of your code runs. The dotted red edge is where GlobalExceptionHandler catches any thrown exception and turns it into a consistent JSON error.

If you can tell those five files back to yourself as one story, you understand this app. All the other code is a variation on that theme.

§ 2 · Design patterns

The patterns in this code, with the problem each one solves

A pattern is not a decoration. It is a solution to a specific problem. If you can name the pattern and the pain that it removes, you understand the choice. Every row below is a real pattern in this codebase, with the file where you can see it at work.

PatternWhere it isThe problem it solves
Dependency Injection GoF-adjacent @RequiredArgsConstructor (or @AllArgsConstructor) + final fields — every controller, and every service that injects a collaborator Classes ask for their collaborators. They do not create them. This makes the classes testable, and no service constructor has a new UserRepository() buried in it.
Layered architecture controllers → services → repositories HTTP concerns stop at the controller edge. Business rules stop at the service edge. SQL stops at the repository edge. Each layer changes for one reason.
DTO (Data Transfer Object) dto/UserResponse · dto/GameRequest · dto/Create/UpdateUserRequest The DTO decouples the API contract from the database schema. A password column on the entity cannot leak into a JSON response, because the DTO does not declare one.
Static Factory Method UserResponse.from(users) The method name shows the mapping direction at the call site. Effective Java, Item 1: prefer static factories to constructors when the name adds information.
Builder GoF Users.builder() · Games.builder() (from Lombok @Builder) A builder makes the construction of objects with many optional fields easy to read. Effective Java, Item 2: use a builder instead of telescoping constructors.
Repository UserRepository · GamesRepository · PurchaseRepository · WishlistRepository · OrderRepository · RewardTransactionRepository An interface abstracts data access. Method names such as findByEmail or existsByUserName become SQL at runtime. You do not write JDBC code by hand.
Proxy GoF Spring Data repository impls · @Transactional wrappers Spring adds behaviour (SQL execution, transaction begin/commit, security checks) around a class, and your source does not change. The object that you inject is a proxy that Spring made at runtime. For a repository interface, it is a JDK dynamic proxy. For a @Transactional service, it is a CGLIB subclass.
Chain of Responsibility GoF The servlet filter chain Each filter does one job and calls filterChain.doFilter(...). One filter applies CORS, one decodes the JWT, and one does authorization. To add a new concern, you add another link to the chain. You do not edit the filters that are already there.
Template Method GoF extends OncePerRequestFilter → override doFilterInternal The framework controls the algorithm. You fill in one hook. That is why you never write "make sure this only runs once per request". The Spring parent class already does it.
Strategy GoF PasswordEncoder ← BCryptPasswordEncoder (in ApplicationConfig) Callers depend on the interface, not on the algorithm. If you replace bcrypt with Argon2, you change one line in one file. The callers do not change.
Adapter GoF Users implements UserDetails The adapter makes a JPA entity fit the shape that Spring Security expects. Authentication can load a "security principal" directly from the users table, with no extra type in the middle.
Front Controller DispatcherServlet (Spring MVC, wired by Boot) One entry point sends every request that comes in to the correct handler. You never write a URL-to-method table by hand. You write annotations on methods, and the front controller does the dispatch.
Singleton (default bean scope) Every @Service, @Component, @RestController Spring makes one instance of the bean per app. This is cheap and fast. It is also the reason that mutable fields on a bean are dangerous, because every request sees the same object. Beans should be stateless.

§ 3 · Real fixes from this repo

Beginner mistake compared with best practice

Every card below shows a real change that this codebase made. The "mistake" panel shows code that was once here (or almost was). The "clean code" panel shows the code that replaced it. The note explains why the fix matters in practice.

1. Field injection → constructor injection on a final field

DISpring
BEGINNER · @Autowired on a field
@RestController
public class GamesControllers {
    @Autowired
    private GamesService gamesService;  // mutable, not final
}
CLEAN · constructor injection by Lombok
@RestController
@RequiredArgsConstructor
public class GamesControllers {
    private final GamesService gamesService;
}

Why this matters: field injection hides the dependency, because no constructor shows it. The field cannot be final. You cannot test the class in a plain unit test without reflection. Constructor injection makes the dependency necessary and makes the class easy to test. In a test, you call new with mocks.

2. JPA entity as the response → a UserResponse DTO

SecurityDTO
BEGINNER · return the entity
@GetMapping("/all")
public ResponseEntity<List<Users>> getAllUsers() {
    return ResponseEntity.ok(service.findAllUsers());
    // Response includes password hash unless a Jackson
    // annotation happens to be in place.
}
CLEAN · map to a record with no password field
@GetMapping("/all")
public ResponseEntity<PagedResponse<UserResponse>> getAllUsers(
        @RequestParam(required = false) String q,
        @PageableDefault(size = 20, sort = "id") Pageable pageable) {
    Page<Users> page = usersService.search(q, pageable);
    return ResponseEntity.ok(PagedResponse.from(page, UserResponse::from));
}

Why this matters: you can hide the password with @JsonProperty(access = WRITE_ONLY) on the entity, but then the "safety" is not by design. It comes from one annotation only. If someone removes that annotation, the hash is public. The DTO makes safety structural. The record does not declare a password field, so no code can serialize one, even by accident.

3. getUsername() compared with getUserName() — a real bug fixed in this repo

JavaSpring Security
BEGINNER · call the UserDetails override by accident
public static UserResponse from(Users user) {
    return new UserResponse(
        user.getId(),
        user.getUsername(),  // ← UserDetails override → returns EMAIL
        user.getEmail(),
        user.getRole().name(),
        user.getPoints());
}
CLEAN · use the entity field getter
public static UserResponse from(Users user) {
    return new UserResponse(
        user.getId(),
        user.getUserName(), // ← hand-written getter for the userName field
        user.getEmail(),
        user.getRole().name(),
        user.getPoints(),
        user.getDisplayName(), user.getAvatarKey(), user.getBio(),
        user.getCountry(), user.getCreatedAt());
}

Why this matters: here, the entity overrides the interface method getUsername() (from UserDetails) to return the email. Spring Security uses this method to find users. The hand-written getUserName() returns the real username field. Lombok does not generate this getter, because the two names differ only in case. The compiler cannot tell you which one you meant. The regression test in UsersEndpointsIT now checks that both fields have the values that a human expects.

4. RuntimeException → 400 catch-all → specific mappings + Exception → 500

@RestControllerAdvice
BEGINNER · blame the client for every bug
@ExceptionHandler(RuntimeException.class)
public ResponseEntity<?> handleRuntime(RuntimeException e) {
    return new ResponseEntity<>(
        Map.of("message", e.getMessage()),
        HttpStatus.BAD_REQUEST);
    // A NullPointerException from a server bug
    // just became "400 Bad Request".
}
CLEAN · specific handlers + 500 backstop (simplified)
@ExceptionHandler({DuplicateResourceException.class, EmailAlreadyExistsException.class,
                    InvalidPasswordException.class, InvalidCheckoutException.class})
public ResponseEntity<?> handleClientError(RuntimeException e) {
    return status(BAD_REQUEST).body(msg(e.getMessage()));
}

@ExceptionHandler(Exception.class)
public ResponseEntity<?> handleUnexpected(Exception e) {
    log.error("Unhandled exception", e);
    return status(INTERNAL_SERVER_ERROR)
        .body(msg("An unexpected error occurred"));
}

Why this matters: a 4xx status says "the client made a mistake". A 5xx status says "the server made a mistake". If you map every RuntimeException to 400, you give false information to callers and hide your stack traces. The clean version logs the trace and returns a generic 500 message. The client sees "something went wrong", and you see the cause in the logs.

5. throw new RuntimeException(...) → a named domain exception

Java
BEGINNER · use the base type
if (userRepository.existsByEmail(user.getEmail())) {
    throw new RuntimeException("Email already in use");
}
CLEAN · a type the handler can catch specifically
if (userRepository.existsByEmail(user.getEmail())) {
    throw new DuplicateResourceException("Email already in use");
}

Why this matters: you cannot send a bare RuntimeException to one handler only. A handler for it also catches every other unchecked exception in the app. A named class lets the @ExceptionHandler catch this specific error. It also lets tests assert on the type, not on a fragile message string.

6. @RequestBody Users → @Valid @RequestBody CreateUserRequest

Security · mass assignmentDTO
BEGINNER · bind the entity directly
@PostMapping("/add")
public ResponseEntity<Users> addUser(@RequestBody Users user) {
    return ResponseEntity.status(CREATED).body(service.addUser(user));
    // Client controls EVERY field — role, points, id.
    // POST { "role": "ADMIN" } → self-promotion.
}
CLEAN · validated DTO, controller maps to entity (simplified)
@PostMapping("/add")
public ResponseEntity<UserResponse> addUser(
        @Valid @RequestBody CreateUserRequest request) {
    Users toCreate = Users.builder()
            .userName(request.userName())
            .email(request.email())
            .password(request.password())
            .points(request.points() != null ? request.points() : 0)
            .role(request.role() != null ? request.role() : Role.USER)
            .build();
    Users created = service.addUser(toCreate);
    return ResponseEntity.status(CREATED).body(UserResponse.from(created));
}

Why this matters: if you bind the entity, you have a mass-assignment vulnerability. The DTO gives you a whitelist of accepted fields. @Valid enforces every constraint annotation on the DTO (@Email, @Size(min=8), @NotBlank) before your handler runs.

7. Matcher order — the first match applies

Security
BEGINNER · general rule first
.requestMatchers("/users/**").hasRole("ADMIN")
.requestMatchers("/users/me").authenticated()
// /users/me matches /users/** FIRST and gets ADMIN-gated,
// so no ordinary user can ever read their own record.
CLEAN · specific rule first
.requestMatchers("/users/me", "/users/me/**").authenticated()
.requestMatchers("/users/**").hasRole("ADMIN")

Why this matters: Spring Security evaluates matchers from top to bottom and stops at the first one that matches. The rule that you meant as the exception must appear before the rule that it is an exception to. The same principle applies to if / else if ladders in your own code.

8. JpaRepository<Users, Long> with an Integer id

Java generics
BEGINNER · guessed the id type
public interface UserRepository
    extends JpaRepository<Users, Long> { }

// Compiles, then at runtime:
// "provided id of the wrong type for class ...Users.
//  Expected: Integer, got Long"
CLEAN · match the entity id type
public interface UserRepository
    extends JpaRepository<Users, Integer> { }

Why this matters: Java erases generics at runtime. As a result, the compiler accepts a repository whose id type does not match the @Id field of the entity. Hibernate finds the problem only at the first query. Read the id declaration of the entity before you write the repository.

9. double price → BigDecimal price

OCA · numeric types
BEGINNER · use a primitive for money
@Column(nullable = false)
private double price;
// double a = 0.1, b = 0.2;
// a + b == 0.3   →   false  (it's 0.30000000000000004)
CLEAN · exact decimal for currency
@Column(nullable = false, precision = 10, scale = 2)
private BigDecimal price;
// Exact base-10 arithmetic; no accumulated rounding.

Why this matters: double and float are base-2 floating point types. They cannot represent most decimal fractions exactly. One cent lost per transaction, across a million transactions, is a real bug. BigDecimal (immutable, exact) is the correct type for money. This exact question appears on 1Z0-808 exam papers.

10. @OneToMany without mappedBy → an extra join table

JPA
BEGINNER · both sides declare ownership
// In Users:
@OneToMany private List<Purchases> purchases;

// Hibernate assumes it owns BOTH sides and generates
// a users_purchases join table you never asked for.
CLEAN · one owner (the FK holder) + mappedBy
// In Users:
@OneToMany(mappedBy = "user",
           cascade  = CascadeType.ALL,
           orphanRemoval = true)
private List<Purchases> purchases;

// mappedBy = "user" says: "Purchases owns the FK column,
// I just navigate to it." No junk table.

Why this matters: in a bidirectional JPA relationship, exactly one side is the owner. The owner is the side whose table holds the foreign key. The other side declares mappedBy = "<field name on the owner>". If you do not declare it, Hibernate creates its own join table, and the result is duplicate rows that are hard to explain.

11. Role taken from the request body → derived server-side from admin.email

Security · authorization
BEGINNER · trust the client
public AuthenticationResponse register(RegisterRequest req) {
    Users u = Users.builder()
        .email(req.getEmail())
        .role(req.getRole()) // ← client sets their own role
        .build();
    ...
}
// POST /register { "email": "...", "role": "ADMIN" }
// You are now the admin.
CLEAN · derived from configured admin email
@Value("${admin.email}")
private String adminEmail;

Role role = request.getEmail().equalsIgnoreCase(adminEmail)
        ? Role.ADMIN
        : Role.USER;

Why this matters: do not trust any input that the client controls. Authorization decisions must come from data that you own (a configured value, a database record, a signed token). They must never come from a field that the caller can change in Postman.

12. Committed jwt.secret → ${JWT_SECRET} from the environment

Security · secrets
BEGINNER · commit the secret
# application.properties (checked into git)
jwt.secret=hR8fA...actualBase64Key...=
CLEAN · resolve from the environment
# application.properties
jwt.secret=${JWT_SECRET}
# The value lives outside git: an environment variable, or the
# gitignored application-local.properties (run with the local profile).

Why this matters: anything that you push to a public repo is compromised at the moment it lands. Assume that scrapers watch public repos. If you rotate a leaked JWT key, you invalidate every token in use, but the alternative is worse. Move all secrets to environment variables or a secrets manager from the start.

§ 4 · Spring, in depth

Annotations — what they do, and what they secretly do

A Spring annotation is a request to the framework: "Please generate the plumbing that I would otherwise write by hand." Every card below expands to show the mechanism behind the annotation, not only its name.

@RestController — @Controller + @ResponseBody

@RestController is @Controller + @ResponseBody on every method. As a result, Spring hands the return value of each method to Jackson (or to the HttpMessageConverter that matches Accept). The converter serializes the value to JSON. Spring does not use it as a view name for a template engine.

Under plain @Controller, if a method returns List<Users>, Spring tries to render a view called "[Users{id=1,...}]". As a result, you get a 500. This is quiz Q1.

@Service, @Repository, @Component — same mechanism, different vocabulary

All three tell Spring "instantiate this class as a bean". They have different meanings, so a reader can see the role of each class. A @Service class holds business logic. A @Repository class does data access, and it also gets JPA exception translation. For infrastructure classes such as filters, @Component is the generic fallback.

Choose the most specific annotation that fits. It costs nothing at runtime. It also documents your intent.

@Configuration + @Bean — factory methods for beans

@Configuration marks a class as a source of bean definitions. Every method that you annotate with @Bean becomes a factory. Spring calls the factory once per scope and registers the result. The default scope is singleton.

Look at ApplicationConfig. passwordEncoder(), authenticationProvider() and userDetailsService() are all beans, which Spring wires together by return type and by parameters. That is why the classes never say new BCryptPasswordEncoder(). They ask for a PasswordEncoder, and Spring supplies the bean that is currently registered under that type.

@Autowired — and why you do not see it here

From Spring 4.3, @Autowired on a constructor is not necessary when the class has exactly one constructor. The Lombok @RequiredArgsConstructor generates that single constructor from final fields, so injection occurs with no @Autowired anywhere. As a result, the dependencies are visible in the constructor signature. The code also has few annotations.

You still see @Autowired on field injection. That is the antipattern that this repo removed.

@Transactional — the proxy trap that surprises everyone once

@Transactional works through a proxy. Spring subclasses your service and wraps the annotated method in a begin/commit/rollback. Thus, calls that go through the proxy get the transaction. Calls that you make within the same class (this.someMethod()) bypass the proxy and lose the transaction. This is the "self-invocation trap".

By default, the transaction rolls back only on unchecked exceptions. If you want checked exceptions to cause a rollback, use @Transactional(rollbackOn = SomeChecked.class). The services in this repo import jakarta.transaction.Transactional. That annotation names the attribute rollbackOn. The Spring annotation calls it rollbackFor.

@Valid and @RequestBody

@RequestBody asks Jackson to deserialize the JSON of the request into the parameter type. Then @Valid runs every Bean Validation constraint on that object (for example @NotBlank, @Email, @Size and @Positive). If validation fails, Spring throws a MethodArgumentNotValidException before your handler runs. GlobalExceptionHandler turns it into a 400 with an errors map that has one entry for each field.

@RestControllerAdvice + @ExceptionHandler — one place, all errors

@RestControllerAdvice is @ControllerAdvice + @ResponseBody. Each @ExceptionHandler method inside it applies to exceptions from any controller in the application. Thus, services only throw, and they know nothing about HTTP. In this repo, every error goes to GlobalExceptionHandler.

@Entity, @Table, @Column — object-to-row mapping

@Entity tells JPA "this class is a persistent type". The @Table annotation overrides the generated table name. The @Column annotation overrides the column name or adds constraints (nullable = false, unique = true, columnDefinition = "TEXT"). Hibernate builds a metamodel from these annotations at boot. Then it generates SQL when it needs it.

This repo sets spring.jpa.hibernate.ddl-auto=validate. Flyway migrations (V1 to V6) build the schema. At startup, Hibernate only checks that every entity matches it. If an entity does not match, the startup stops. The value update, which the repo used before Flyway, lets Hibernate change the schema itself. That is a convenience in development and an operational hazard in production.

@OneToMany / @ManyToOne and FetchType.LAZY

In a bidirectional relationship, one side owns the foreign key. The other side declares mappedBy = "<field name on the owning side>". This is Mistake #10 above.

FetchType.LAZY delays the load of an association until you navigate it. You need it on @ManyToOne. If you do not use it, every query pulls the whole graph. Be careful of LazyInitializationException. If you try to load a lazy field outside a transaction (for example, from a detached entity such as the JWT principal), this exception occurs.

@Enumerated(EnumType.STRING) — and why not ORDINAL

EnumType.STRING stores the name of the enum constant ("USER", "ADMIN"). EnumType.ORDINAL stores its position (0, 1). If you change the order of the enum constants one time, every ordinal in the database refers to the wrong value. The compiler does not warn you. Use STRING.

@JsonIgnore / @JsonProperty(access = WRITE_ONLY)

@JsonIgnore tells Jackson to omit this field in both directions. @JsonProperty(access = WRITE_ONLY) accepts the field on input but omits it on output. This is the pattern for passwords on entities. But both give only incidental safety. The structural fix is a DTO that never declares the field (see Mistake #2).

@AuthenticationPrincipal — inject "the current user"

@AuthenticationPrincipal is a parameter-level annotation. It gets SecurityContextHolder.getContext().getAuthentication().getPrincipal() and casts it to the parameter type. In this app, the principal is a Users, because userDetailsService() returns the entity. Thus, @AuthenticationPrincipal Users user is the clean way to get the current user with no boilerplate.

@Value("${...}") — pull config into a bean

@Value injects a resolved property (from application.properties, an environment variable or a YAML file) into a field. In JwtService, @Value("${jwt.secret}") reads the line jwt.secret=${JWT_SECRET} from application.properties. Then Spring resolves ${JWT_SECRET} from the highest source that defines it. The order is JVM system properties, then environment variables, then application-local.properties when the local profile is active. That is the mechanism behind Mistake #12.

§ 5 · Java fundamentals, exam-badged

What this codebase teaches you about the language

Each concept below has a badge. The OCA 1Z0-808 exam covers Java SE 8, but this codebase is Java 17. As a result, some of the most idiomatic code here (records, var, Stream.toList()) is explicitly outside the exam. Read the badges before you assume anything.

On 1Z0-808Autoboxing

Integer compared with int — why the points null-guard exists

In UsersService.updateUser, if a client sends an update with no points field, Jackson leaves the Integer points of the DTO as null. The entity field is also an Integer, so setPoints(null) erases the stored balance and shows no error. That is why the fix reads:

if (updatedUser.getPoints() != null) {
    existing.setPoints(updatedUser.getPoints());
}

OCA trap: if you change the field to a primitive int, the same assignment unboxes null and throws NullPointerException. On 1Z0-808, the question about boxing and unboxing appears as a puzzle: "why does this line throw an NPE?" The answer is that an assignment to an int calls .intValue() on null.

On 1Z0-808enum

enum Role { USER, ADMIN }

An enum is a class that you declare with a fixed set of instances. You can add fields, constructors, and methods to it. Role.ADMIN.name() returns "ADMIN". Hibernate stores this value in the database (through @Enumerated(EnumType.STRING)), and the backend puts the same value in the JWT as a claim.

OCA trap: know the difference between name() (final, returns the constant name) and toString() (you can override it).

On 1Z0-808Interfaces

Interfaces with default methods — UserDetails has them

From Java 8, an interface can hold method implementations with default. This lets UserDetails add methods and not break the classes that already implement it. When you write Users implements UserDetails, you can keep the defaults and override only the methods that you need. In Spring Security 6.3, the four account-status checks are defaults that return true. But Users overrides all four anyway. Three return true, and isEnabled() returns the enabled field.

On 1Z0-808Multi-catch

Multi-catch: catch (JwtException | UsernameNotFoundException e)

This code is from JWTAuthenticationFilter. One catch block handles more than one exception type, with | between the types. The parameter is effectively final.

OCA trap: the types in a multi-catch must not be in an inheritance chain with each other. For example, you cannot write catch (RuntimeException | IllegalStateException e).

On 1Z0-808Lambdas

Lambda that implements a functional interface

This code is from ApplicationConfig.userDetailsService():

return username -> repository.findByEmail(username)
        .orElseThrow(() -> new UsernameNotFoundException("User not found"));

UserDetailsService is a functional interface (it has one abstract method, loadUserByUsername). The lambda is the implementation. This is standard 1Z0-808 material.

On 1Z0-808Optional

Optional.orElseThrow

return userRepository.findById(id)
    .orElseThrow(() -> new ResourceNotFoundException("User not found with id: " + id));

Java 8 added Optional. orElseThrow(Supplier) returns the value, or it throws the exception that the supplier returns. Use it instead of .get(), because .get() throws NoSuchElementException with no diagnostic message.

On 1Z0-808String

String immutability and equalsIgnoreCase

request.getEmail().equalsIgnoreCase(adminEmail) does a case-insensitive comparison, and it does not allocate lower-case copies. Strings are immutable, so the JVM can pool them and cache literals. Because of this, == sometimes seems to work. It does not work reliably. Always compare with .equals() or .equalsIgnoreCase(). This is a big 1Z0-808 topic.

Java 16+ · not on 1Z0-808

record — used everywhere in dto/

public record UserResponse(
        Integer id, String userName, String email,
        String role, Integer points,
        String displayName, String avatarKey, String bio,
        String country, LocalDateTime createdAt) { ... }

A record gives you private final fields, a canonical constructor, accessors, and equals/hashCode/toString. You do not write any of them. Its design makes a record immutable. Records are not on 1Z0-808. If you prepare for that exam, the exam tests you on the plain-class equivalent, not on the record.

Java 9+ · not on 1Z0-808

List.of(...) — immutable collection factory

This code is from Users.getAuthorities():

return List.of(new SimpleGrantedAuthority("ROLE_" + role.name()));

It returns an unmodifiable list. It is cheaper and clearer than Collections.unmodifiableList(Arrays.asList(...)). This factory is not on 1Z0-808. On the exam, use Arrays.asList or a mutable list instead.

Java 16+ · not on 1Z0-808

Stream.toList()

This code is from WishlistService.findMine:

return wishlistRepository.findByUserOrderByAddedAtDesc(managedUser(email)).stream()
        .map(WishlistResponse::from)
        .toList();

It is shorter than .collect(Collectors.toList()), and it returns an unmodifiable list. The 1Z0-808 equivalent is .collect(Collectors.toList()). Also, Streams past the basics are on the OCP exam, not on the OCA exam.

Java 10+ · not on 1Z0-808

var — local variable type inference

AuthenticationService uses it in var newUser = Users.builder().... The compiler infers the type from the initializer. It works only for local variables. It does not work for fields, method parameters, or return types. This feature is not on 1Z0-808.

OCP (1Z0-809)Streams

Method references: UserResponse::from

ClassName::method is a shorthand for a lambda that only calls that method. Here, it is equivalent to user -> UserResponse.from(user). The controller passes it as a Function to PagedResponse.from(page, UserResponse::from), which hands it to Stream.map. The OCP exam covers Streams and method references, but 1Z0-808 does not.

On 1Z0-808Exceptions

Checked and unchecked exceptions

Every custom exception in this codebase (ResourceNotFoundException, DuplicateResourceException, EmailAlreadyExistsException, InvalidPasswordException, InvalidCheckoutException) extends RuntimeException, so each one is unchecked. As a result, no method needs a throws clause, callers need no boilerplate, and the default rollback rule of @Transactional applies. Checked exceptions (classes that extend Exception directly) make every caller handle or declare them. Prefer unchecked exceptions for errors in the program and checked exceptions for conditions that a caller can recover from. This topic is on the 1Z0-808 exam.

On 1Z0-808equals / hashCode

Why every entity here has custom equals and hashCode

JPA entities have a mutable id (null before the first save, with a value after it). If equals compares all fields, two instances of "the same" user are not equal until you save both of them. The entities in this codebase compare by id only. Their hashCode returns getClass().hashCode(), so the value is stable for the full lifecycle of the entity. This is a classic JPA hazard. Also, equals/hashCode contracts are 1Z0-808 territory.

On 1Z0-808Modifiers

final on fields — what it guarantees

final on a field means that the code assigns the field exactly one time, either at the declaration or in the constructor. It does not mean that the referenced object is immutable. You can still change the object that the field refers to. In this codebase, final on injected fields is a contract. It says that the constructor sets each dependency and that nothing replaces it later.

On 1Z0-808Access

Access modifiers — public, protected, package-private, private

The DTOs in dto/ are public records because the API surface reads them. The three auth DTOs in authentication/ are still Lombok @Data classes. Fields on entities are private, and other code accesses them through the getters that Lombok generates. Package-private (the default, with no modifier) is useful for helpers. It is more than "public that forgot the word".

§ 7 · Assessment prep

What rigorous technical assessments test

This section aims at the things that graduate programmes and recruitment assessments (BBD-style, for example) test. They do not test fact recall. They test whether you can justify a design choice. Note that this is general preparation for that class of assessment. It does not copy the paper of any specific company.

The four things that they test under the code question

  1. Can you explain why? "Why is this a service, not a helper class in the controller?" The answer is the separation of layers, testability and the transaction boundary.
  2. Do you know when to use a pattern? The question is not "list five design patterns". It is "you have three payment providers with different APIs. How do you structure that?" A good answer names Strategy and gives the reason.
  3. Can you find a security issue in code that you did not write? §3 covers mass assignment (card 6), a leaked password hash (card 2) and secrets in git (card 12). It also covers two role mistakes: the rule order in card 7 and a role taken from the request in card 11. Quiz Q2 covers IDOR. No §3 card covers how the backend hashes passwords. See the Strategy row of §2 (PasswordEncoder ← BCryptPasswordEncoder).
  4. Can you talk about trade-offs? "Why 400 for duplicate email and not 409?" The answer is a real trade-off between HTTP correctness and the stability of the frontend contract. It is not a choice between right and wrong.

SOLID walkthrough on this codebase

  • S — Single Responsibility. Controllers do HTTP, services do business rules, and repositories do persistence. The exception handler is a single class because "turn thrown exceptions into JSON" is one responsibility.
  • O — Open/Closed. The filter chain is open for extension (you add a link) and closed for modification (the current filters do not change).
  • L — Liskov substitution. Users implements UserDetails. Anywhere that Spring Security expects a UserDetails, a Users works, and it does not surprise the caller.
  • I — Interface segregation. UserDetailsService has one method. Callers do not depend on methods that they do not use.
  • D — Dependency Inversion. UsersService depends on PasswordEncoder (an interface), not on BCryptPasswordEncoder (a concrete class). To change the algorithm, you change one line in ApplicationConfig.

Things you should know how to draw on a whiteboard

  • The filter chain, in order, with what each filter does.
  • The four layers of the app, and one file name per layer.
  • The register flow: what happens after the POST arrives and before the token goes out.
  • The rule table from SecurityConfiguration, in order, with an explanation of why "first match wins" matters.
  • The exception → HTTP status mapping (200/201/204 successes and 400/401/403/404/500 errors).
